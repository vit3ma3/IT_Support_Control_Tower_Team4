# IT Support Control Tower — пользовательские сценарии v0.1

Роль R3 (UI / Frontend). Черновик для обсуждения командой.
Основа: Use Case v0.3, портреты пользователей v0.1, кейс № 19 и `Product Foundation v0.1`.

Названия экранов и элементов интерфейса в сценариях это предложение R3, в кейсе их нет. Пороги SLA взяты из примера кейса: P1 — 15/60 мин, P2 — 30/240 мин, P3 — 120/480 мин (реакция/решение), окончательно задаются в README.

## SC-01. Загрузить данные из CSV

| Поле | Описание |
|---|---|
| Актор | Аналитик |
| Цель | Получить в системе тикеты и события для расчёта SLA |
| Предусловия | Справочники очередей и исполнителей заполнены; цели SLA заданы для P1, P2, P3; есть файлы `tickets`, `events`, `sla_targets` |
| Триггер | Нужно построить отчёт за новый период |

**Основной ход**
1. Аналитик открывает экран «Импорт данных».
2. Выбирает файлы CSV для таблиц `tickets`, `events` и `sla_targets`.
3. Нажимает «Загрузить».
4. Система проверяет данные: хронологию событий, наличие целей SLA для каждого приоритета, ссылки на очередь и исполнителя, уникальность `first_response` и `resolved`, `closed_at ≥ created_at`.
5. Система исключает дубликаты по ключам `ticket_id` и `(ticket_id, event, ts)`.
6. Система показывает итог: сколько тикетов и событий загружено, сколько отклонено.

**Альтернативные ходы**
- 4a. Найдены ошибки: система загружает корректные строки и показывает кнопку «Открыть протокол ошибок» (см. SC-02).
- 2a. Выбран файл не в формате CSV или без обязательных колонок: система сообщает об этом до загрузки и ничего не загружает.

**Результат:** корректные данные загружены, отчёт можно строить.
**Критерий приёмки:** в наборе не менее 300 тикетов; у каждого тикета есть события `first_response` и `resolved`.

## SC-02. Разобрать ошибки валидации

| Поле | Описание |
|---|---|
| Актор | Аналитик |
| Цель | Понять, какие строки не прошли проверку и почему |
| Предусловия | Выполнена загрузка (SC-01), найдены ошибки |
| Триггер | Система сообщила об отклонённых строках |

**Основной ход**
1. Аналитик открывает протокол ошибок.
2. Видит список: номер строки, `ticket_id`, нарушенное правило (например, «`resolved` раньше `first_response`»).
3. Фильтрует список по типу правила.
4. Исправляет исходный файл и загружает его снова (SC-03).

**Альтернативные ходы**
- 2a. Ошибок нет: протокол пустой, система показывает сообщение «Ошибок не найдено».

**Результат:** аналитик знает, что исправить в исходных данных.

## SC-03. Повторно загрузить тот же файл

| Поле | Описание |
|---|---|
| Актор | Аналитик |
| Цель | Загрузить исправленный или повторный файл без дублей |
| Предусловия | Часть данных уже загружена |
| Триггер | Файл исправлен после SC-02 или загружается повторно |

**Основной ход**
1. Аналитик загружает файл, как в SC-01.
2. Система сравнивает строки с уже загруженными по ключам `ticket_id` и `(ticket_id, event, ts)`.
3. Совпавшие строки пропускаются, новые добавляются.
4. Система показывает итог: добавлено, пропущено как дубликаты, отклонено.

**Результат:** количество тикетов и событий не удваивается.
**Критерий приёмки:** повторная загрузка того же файла не меняет метрики отчёта.

## SC-04. Оценить SLA за период

| Поле | Описание |
|---|---|
| Актор | Руководитель ИТ |
| Цель | Быстро понять, выполняется ли SLA по приоритетам |
| Предусловия | Данные загружены; цели SLA заданы |
| Триггер | Регулярный просмотр или подготовка отчёта о качестве сервиса |

**Основной ход**
1. Руководитель открывает отчёт «SLA и загрузка».
2. Выбирает период в фильтре.
3. Видит сводку: среднее и медиана времени реакции и решения, доля нарушений SLA.
4. Видит столбчатую диаграмму SLA по приоритетам P1, P2, P3.
5. Видит рядом с отчётом дату расчёта и применённые пороги SLA.

**Альтернативные ходы**
- 2a. За выбранный период нет данных: система сообщает об этом и предлагает изменить период.
- 4a. Руководитель хочет понять причину нарушений: переходит к SC-05.

**Результат:** руководитель знает, по каким приоритетам SLA нарушается.
**Критерий приёмки:** время реакции = `first_response.ts − created_at`, время решения = `resolved.ts − created_at`; нарушение, когда факт больше цели.

## SC-05. Найти перегруженную очередь или исполнителя

| Поле | Описание |
|---|---|
| Актор | Руководитель ИТ; Менеджер очереди (только своя очередь, допущение) |
| Цель | Найти, где неравномерная загрузка, и перераспределить работу |
| Предусловия | Отчёт построен (SC-04) |
| Триггер | Высокая доля нарушений или жалобы на задержки |

**Основной ход**
1. Пользователь открывает блок «Загрузка».
2. Видит распределение загрузки по очередям и исполнителям (heatmap или диаграмма Ганта): активные тикеты от `assigned` до `resolved` в день.
3. Фильтрует по очереди и исполнителю.
4. Находит ячейку с высокой загрузкой и открывает список тикетов за этот день.
5. Открывает отдельный тикет и видит его события (UC-15, Should).

**Альтернативные ходы**
- 3a. Менеджер очереди: фильтр по очереди выбран заранее (решение команды).
- 4a. Детализации нет в MVP: пользователь видит только агрегированные показатели.

**Результат:** определены очередь и исполнитель с перегрузкой.

## SC-06. Посмотреть динамику SLA по приоритетам

| Поле | Описание |
|---|---|
| Актор | Руководитель ИТ |
| Цель | Увидеть, как менялась доля нарушений во времени |
| Предусловия | Данные загружены за несколько периодов |
| Триггер | Нужно понять, улучшается ситуация или ухудшается |

**Основной ход**
1. Руководитель открывает блок «Динамика».
2. Выбирает гранулярность: по дням или по неделям (решение команды).
3. Видит линию или столбцы по приоритетам P1, P2, P3.
4. При необходимости сравнивает два периода (UC-16, Should).

**Результат:** руководитель видит тренд.

## SC-07. Экспортировать отчёт в CSV

| Поле | Описание |
|---|---|
| Актор | Аналитик, Руководитель ИТ |
| Цель | Передать результаты в BI или коллегам |
| Предусловия | Отчёт построен с выбранными фильтрами |
| Триггер | Нужно выгрузить результаты |

**Основной ход**
1. Пользователь нажимает «Экспорт в CSV».
2. Система формирует файл с полями `queue`, `priority`, `resp_avg`, `resolve_avg`, `breach_rate`, `load_avg` по текущим фильтрам.
3. Система фиксирует дату расчёта и пороги SLA (UC-23).
4. Пользователь скачивает файл.

**Альтернативные ходы**
- 2a. По выбранным фильтрам нет данных: система предупреждает и не создаёт пустой файл.

**Результат:** файл CSV, воспроизводимый по зафиксированным параметрам.
**Критерий приёмки:** значения в файле совпадают с отчётом на экране.

## SC-08. Проверить параметры расчёта

| Поле | Описание |

| Цель | Убедиться, с какими параметрами получена цифра |
| Предусловия | Был выполнен расчёт или экспорт |

**Результат:** аналитик подтверждает или объясняет разницу в цифрах.

## SC-09. Настроить цели SLA

| Поле | Описание |
|---|---|
| Актор | Руководитель ИТ (исполнитель настройки нужно подтвердить командой) |
| Цель | Задать целевые значения SLA для приоритетов |
| Предусловия | У пользователя есть права на настройку |
| Триггер | Изменились нормативы или первичная настройка системы |

**Основной ход**
1. Руководитель открывает экран «Цели SLA».
2. Задаёт для P1, P2 и P3 целевое время реакции и решения в минутах.
3. Нажимает «Сохранить».
4. Система проверяет, что цели заданы для всех трёх приоритетов.
5. Новые пороги применяются к следующим расчётам.

**Альтернативные ходы**
- 4a. Не хватает цели для приоритета: система не сохраняет и указывает, чего не хватает.
- 2a (Should). Руководитель выбирает режим расчёта (календарное или рабочее время) и задаёт правила эскалации.

**Результат:** цели SLA заданы, расчёты используют новые пороги.

## SC-10. Посмотреть риски нарушения SLA

| Поле | Описание |
|---|---|
| Актор | Руководитель ИТ |
| Цель | Увидеть открытые обращения, которые скоро нарушат SLA |

**Основной ход**

3. Сортирует по приоритету и оставшемуся времени.

**Результат:** руководитель видит, какие обращения требуют внимания.

## SC-11. Вести справочники и роли

| Поле | Описание |
|---|---|
| Актор | Администратор 1С |
| Цель | Справочники актуальны, права выданы по ролям |
| Предусловия | Есть права администратора |
| Триггер | Новая очередь, новый сотрудник, изменение состава |

**Основной ход**
1. Администратор открывает справочник очередей и исполнителей.
2. Добавляет или изменяет запись.
3. Открывает настройку ролей и назначает права: операторы вводят события, аналитики смотрят отчёты, руководитель настраивает нормативы.
4. Система сохраняет изменения.

**Альтернативные ходы**
- 2a. Запись используется в загруженных тикетах: система не позволяет удалить её.

**Результат:** импорт проходит проверку ссылок, пользователи видят только свои функции.

## SC-12. Зарегистрировать события обращения

Опционально: нужен, если ввод событий операторами входит в MVP.

| Поле | Описание |
|---|---|
| Актор | Оператор 1-й линии, Оператор 2-й линии |
| Цель | Внести события так, чтобы они корректно попали в метрики |
| Предусловия | Тикет создан и есть права ввода событий |
| Триггер | Изменился статус обращения |

**Основной ход**
1. Оператор открывает тикет.
2. 1-я линия отмечает назначение (`assigned`) и первую реакцию (`first_response`); 2-я линия отмечает решение (`resolved`). Распределение событий по линиям это толкование R3.
3. Система проверяет хронологию `created_at ≤ assigned ≤ first_response ≤ resolved ≤ closed_at` и то, что `first_response` и `resolved` не дублируются.
4. Система сохраняет событие.

**Альтернативные ходы**
- 3a. Хронология нарушена или событие уже есть: система не сохраняет и объясняет причину.

**Результат:** события тикета корректны и пригодны для расчёта.

## Что нужно решить, прежде чем сценарии станут окончательными

1. Входит ли ввод событий операторами в MVP (SC-12).
2. Есть ли в данных открытые обращения (SC-10, UC-15).
3. Как выбирается очередь у менеджера очереди (SC-05).
4. Гранулярность динамики: по дням или по неделям (SC-06).
5. Кто настраивает цели SLA и ведёт справочники (SC-09, SC-11).
