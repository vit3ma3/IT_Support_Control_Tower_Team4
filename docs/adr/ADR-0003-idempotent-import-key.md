## Контекст

Повторный импорт одинакового набора не должен создавать дубликатов и менять показатели (устав, критерий 9; M-13). Сценарии SC-01 и SC-03 предлагают ключи `ticket_id` и `(ticket_id, event, ts)`. Одновременно проверка V5 требует, чтобы `first_response` и `resolved` были единственными в пределах обращения.

## Рассмотренные варианты

1. **Ключ события `ticket_id + event_type + ts`.** Повтор той же строки распознаётся как дубль; второе событие того же типа с другим временем проходит ключ, но ловится проверкой V5.
2. **Ключ события `ticket_id + event_type` для `first_response` и `resolved`.** Повторная строка с другим временем молча заменила бы событие или была бы пропущена — исправления данных становятся невидимыми.
3. **Хэш всей строки файла.** Зависит от форматирования (пробелы, порядок колонок), ненадёжен.

## Решение

- Обращение: ключ `ticket_id`. Если обращение с таким ключом уже есть и все поля совпадают — строка пропускается как дубликат; если поля отличаются — обращение отклоняется с ошибкой «обращение уже загружено с другими данными» (исправление ранее загруженных записей — вопрос раздела 4 MoSCoW, до решения не поддерживается).
- Событие: ключ `ticket_id + event_type + ts` (вариант 1) плюс проверка уникальности V5 для `first_response` и `resolved` с учётом уже загруженных событий.

## Последствия

- Повторная загрузка контрольного набора даёт итог «добавлено 0, пропущено 8 обращений и 23 события» (T-09).
- Исправленный файл с новым временем события будет отклонён по V5 — исправления делаются через удаление пакета загрузки (вне MVP) или новую ИБ; это записано как ограничение.
- Время сравнивается после приведения к единому формату `YYYY-MM-DD HH:MM:SS` (компонент К1).
